# eDHR 业务知识本体模型

## 目标

将 eDHR 中散落在前后端代码、数据库字段、页面说明和业务文档中的业务知识，整理为结构化、可查询、可解释的业务知识模型。该模型服务于两类场景：

1. 研发和实施人员查看业务关系、规则、来源和影响范围。
2. 客户通过问答页面理解当前产品已经发布的业务逻辑。

内部规划、待开发能力和技术路线只属于研发知识库，不进入客户知识视图。

本模型不是让客户在运行环境中自由修改业务规则的后台，也不把大模型作为生产执行引擎。

## 核心判断

“本体建模”这个方向是准确的，但实际落地应采用四层模型：

```text
概念本体：有哪些对象和关系
业务事实：当前租户有哪些真实对象和配置
业务规则：什么事件下什么条件成立、产生什么结果
执行适配：如何调用确定性的生产服务完成动作
```

本体回答“是什么”，规则回答“何时允许或阻断”，执行适配负责“怎么可靠地做”。四层不能混成一张自由格式的图。

## 维护方式

前期不提供用户修改本体和规则的页面。它们属于产品研发资产，由产品升级、标准功能开发或客户二开维护，进入代码评审和发布流程。

运行环境只读取随产品版本发布的知识模型。数据库可以保存编译后的查询投影，但不能成为一套脱离代码版本、由用户随意编辑的第二套真相。

每次产品发布生成一个知识模型版本，例如：

```text
eDHR 0.3
  ontologyVersion: 0.3.6
  ruleSetVersion: 0.3.6
  executionContractVersion: 0.3.6
```

生产批次仍然保存使用的产品制程版本、规则集版本和执行快照。这不是为了支持客户编辑，而是为了让产品升级后仍能解释历史业务为什么这样流转。

## 智能体协作

`docs/knowledge/` 是机器可读的业务知识权威基线，本文是便于人员阅读的架构投影。两者不一致时，必须核对已确认的业务决策和实现证据并修正偏差，不能让人员阅读文档静默覆盖结构化基线。

用户只负责确认产品决策和真正的业务歧义，不负责填写 YAML、证据索引或智能体交接表。主智能体在正常业务沟通中自动提取已确认结论，区分推断和未决问题，并生成符合 `docs/agents/agent-handoff-contract.md` 的决策包。

主智能体还应在同一决策包中按 L1 或 L2 风险维护需求影响分析和扩展路径选择。本体作为结构化系统地图帮助定位业务关系和实现证据，但影响分析不是自动完整依赖图，也不是新增独立审批流程。L1 只保留精简摘要，L2 才完整分析传递影响、兼容迁移、快照、审计和权限；同一功能切片连续调试时增量更新一次，不得重复建模或阻塞无依赖编码。具体效率边界以 `AGENTS.md` 为准。

长期协作职责如下：

- 主智能体负责业务沟通、业务实现和基础测试。
- 业务知识本体建模智能体依据已确认决策维护 `docs/knowledge/`，核对概念、关系、规则、决策、证据和执行契约的一致性，但不修改业务运行代码。
- 质量验证智能体独立审查需求、知识模型、实现和证据，并按风险执行 CRUD、接口、端到端、视觉、审计、迁移和回归验证；默认只报告问题，不参与修复。

业务语义发生变化时必须完成本体门禁；代码、数据库、接口、交互或客户可见行为发生变化时必须完成质量门禁。适用门禁的结果满足 `AGENTS.md` 定义的完成不变量后，任务才能宣告完成。角色通过每项任务按需实例化，长期上下文由 Git 版本化的知识资产和角色契约保持，而不是依赖某个永不结束的对话。

## 核心概念

| 概念 | 类型 | 说明 |
|------|------|------|
| 物料 | 业务事实 | 产品管理的来源；类型为产品或半成品时派生为产品 |
| 车间 | 业务事实 | 租户级独立维护的无版本主数据，包含编码、名称、描述和状态 |
| 产线 | 业务事实 | 通过 workshop_id 引用一个车间的生产组织单元 |
| 产品 | 业务概念 | 物料管理派生出的生产对象，不独立维护主数据 |
| 产品制程版本 | 业务配置 | 产品下可并行存在的具体制程配置 |
| 工艺路线版本 | 业务事实 | 产品制程版本选择的路线 |
| 工序 | 业务概念 | 工艺路线中的执行节点 |
| DHR 模板版本 | 业务事实 | 产品制程绑定的 DHR 目录定义 |
| DHR 目录项 | 业务概念 | DHR 下可被工序绑定的表单目录项 |
| 表单模板版本 | 业务事实 | DHR 目录项实际引用的受控表单版本 |
| SOP 文档版本 | 业务事实 | 工序执行时需要查看的指导文件 |
| 工序绑定 | 配置事实 | 工序与表单、SOP 和规则的关系 |
| 生产批次/SN | 运行事实 | 执行具体产品制程版本的业务主体 |
| 执行快照 | 运行事实 | 生产对象或作业实例创建时冻结的版本、配置和命中规则依据 |
| 作业模板 | 业务配置 | 可复用的生产作业定义，包含名称、编码、描述、流程配置和适用规则；本体不采用父子业务版本管理 |
| 作业流程版本 | 业务配置 | 作业模板的流程配置版本；草稿、已发布和历史版本分层管理，当前已发布版本对外可用 |
| 作业适用规则 | 配置事实 | 将作业模板应用于全局、指定生产范围或例外排除范围的规则 |
| 作业实例 | 运行事实 | 未来生产执行按适用规则自动匹配后创建，并使用创建时冻结执行依据推进的运行对象 |
| 作业执行快照 | 运行事实 | 作业实例创建时冻结的作业模板、已发布流程版本、命中规则和流程配置快照 |

## 关系模型

```text
产线 --引用--> 车间
物料 --派生为--> 产品
产品 --拥有多个并行版本--> 产品制程版本
产品制程版本 --绑定--> 工艺路线版本
产品制程版本 --绑定--> DHR 模板版本
工艺路线版本 --包含--> 工序
工序 --引用--> DHR 目录项
DHR 目录项 --指向--> 表单模板版本
工序 --引用多个--> SOP 文档版本
产品制程版本 --被显式选择于--> 工单/批次
批次 --冻结为--> 执行快照
```

关键关系必须有来源、版本、适用范围和证据，不只保存两个 ID。问答需要知道“这个表单为什么出现在这个工序”，所以需要沿着 `制程版本 -> DHR版本 -> 目录项 -> 表单版本 -> 工序绑定` 追溯。

### 车间主数据投影

车间在数据模块的“工厂建模”分组下独立维护，不采用业务版本、发布或复制版本模型。当前权威字段只有车间编码、车间名称、描述和状态；不强制归属工厂，编码在同一租户内唯一。旧表的 site_id 和按工厂唯一索引是待迁移的历史实现，不再定义当前业务语义。未来是否恢复工厂关联尚未确认，不属于当前规则。

新建车间默认启用。停用车间不得被新业务选择，已有历史引用仍保留并可展示。产线当前仍通过 workshop_id 引用车间；只要车间存在任何产线或其他业务引用，就锁定车间编码并禁止删除，但名称、描述和状态仍可修改。未被引用时可修改编码或删除。车间新增、修改和删除都必须记录变更前后快照，启用或停用按修改审计。

### 生产作业模板配置投影

作业模板属于“生产 / 生产配置 / 作业模板”，而产品管理、产品簇和工艺路线仍属于数据主数据菜单。流程中心保留审核流程模板和流程实例。作业模板本体不引入父子业务版本；只有流程配置具有草稿、已发布和历史版本。新建作业模板首次进入流程配置时，前端临时显示含开始和结束边界节点的 V1 草稿，用户保存或发布后才落库；临时或首次持久化草稿默认不在开始和结束节点之间创建连线。同一模板只保留一个编辑中草稿；草稿画布可定义表单填写、消息通知、人工确认和条件分支节点及连线。条件节点使用有序 conditionBranches 和唯一 conditionDefaultBranch：每个条件分支独立保存结构化 AST、字段目录版本和字段显示快照，按数组顺序求值并命中第一个满足分支，否则走唯一默认分支；条件节点每个分支出口最多一条线，普通节点和开始节点最多一条出口，流程不支持并行节点。输入只接受 conditionBranches[].conditionRule 与 conditionDefaultBranch；config.conditionRule、分支 rule 以及固定 condition-true/condition-false 出口均不属于当前契约，旧结构不提供兼容读取或转换。上述配置和发布语义不代表运行时字段真实来源、条件求值、实例快照或节点推进已经实现。发布会冻结该版本并自动创建继承配置的下一草稿。若草稿被放弃，用户复制任一已发布流程时系统创建继承配置的下一号草稿，使后续变更无需手工新建版本。适用规则引用作业模板并在未来运行时解析其当前已发布流程版本，不能手工绑定草稿或历史流程；无当前已发布流程的作业仍在适用规则选择器展示，但不可选并提示“该作业尚未发布作业流程版本”。

```text
作业模板 --拥有零到多个--> 作业流程版本
作业模板 --拥有零到多个--> 作业适用规则
作业适用规则 --运行时解析--> 当前已发布流程版本
未来生产上下文 --按适用规则自动匹配--> 作业模板
作业实例 --冻结--> 作业模板 + 当前已发布流程版本 + 命中规则快照 + 流程配置快照
```

作业模板、流程版本和适用规则的新增、编辑和删除均需审计，并保留变更前后快照；对既有但没有审计事件的作业模板，迁移必须写入来源为 SYSTEM、操作者为“系统”、动作为 `BASELINE` 的历史基线事件。该事件仅建立迁移时的追溯起点，不得伪称为原始用户创建。已发布流程版本本身不可单独删除。作业模板删除只受适用规则引用阻断：存在任何适用规则时禁止删除；没有适用规则时，无论模板是否存在草稿、历史流程或当前已发布流程，都允许在同一事务中删除模板及其全部流程配置。该删除规则取代“存在已发布流程即禁止删除父模板”的历史语义。适用规则的优先级固定由 `ruleType` 派生：`EXCEPTION` 例外排除高于 `SCOPED` 指定范围，高于 `GLOBAL` 全局适用；用户不能输入、修改或选择优先级，客户页面不展示优先级。作业适用规则不存在用户可控的启用或停用状态，所有保存的 WORK 规则均为有效规则；共享实体字段保留不得改变审核流程绑定规则的既有语义。作业定义列表显示绑定规则数量，并在 hover 中展示规则及范围；点击整行按既有 RDO 规范打开详情与数据审计，流程配置、编辑和删除由操作栏承载。作业定义和作业适用规则是并列页签，流程配置不承载适用规则。作业适用规则查询仅按作业名称或编码、适用方式、产品簇、产品和工序投影与筛选，状态列和启用停用筛选不进入该投影，未限定的范围显示为“不限”。新增或编辑适用规则时，弹窗只允许选择有当前已发布流程的作业，并显示其当前已发布流程及只读预览入口；无当前已发布流程的作业仍展示但不可选，提示“该作业尚未发布作业流程版本”。弹窗根据作业、适用方式和范围实时生成规则摘要；草稿、历史流程与可编辑优先级均不进入该配置投影。未来生产执行根据上下文按适用规则自动匹配作业，不在产品或工序配置中手工引用。创建作业实例时冻结作业模板、创建时当前已发布流程版本、命中规则快照和流程配置快照。生产执行、作业实例、运行时解析和快照落库仍属于后续能力。

### 表单流程与绑定字段权限投影

表单流程模板不绑定具体表单，因此可以复用于多个表单。表单流程版本只保存流程节点、连线和可选的主体来源。字段权限按权限配置组治理：填报阶段一个权限组可包含多个填报主体，审批阶段每个审批节点本身就是一个权限组，节点内多个审批主体共享该组的默认权限和字段例外；不再按单个主体平铺配置。未配置填报主体/权限组时所有已认证用户可填报，未配置审批主体时所有已认证用户可审批。开放范围不通过展开全量用户实现，仍受认证、流程实例、节点和任务状态约束。流程设计页不配置具体字段，也不再使用流程字段、字段槽位或字段映射作为新配置入口。

表单流程的审批主体和填报权限主体使用同一个公共主体选择模型。第一版只支持系统中已有稳定主数据与成员关系的用户、部门和角色，不提供用户组、部门负责人或业务责任人空壳选项；当前 Role 在产品中承担“岗位角色”语义，不另拆岗位维度。部门主体默认覆盖本部门及下级，也可配置为仅本部门，展示和持久化都必须明确范围。部门和角色不在流程发布或业务启动时冻结人员名单：审批节点到达时按最新关系解析候选人，填报权限在用户访问时按最新关系判断。公共主体解析器及通用工作流多候选任务关系已实现：节点进入时创建一个逻辑任务并冻结候选人与来源，任一候选完成后关闭其他候选；字段权限运行时、表单流程实例、退回至填报阶段和外层作业同步推进仍属于后续能力。

作业流程的表单填写节点必须绑定一个当前生效的表单模板版本，但表单流程本身可选；不需要审批流程时可以不配置表单流程并发布。只有实际绑定已发布表单流程版本后，系统才读取该流程的权限配置组和按钮事件，并校验字段例外、事件绑定和签名字段。绑定后才读取表单版本真实存在的稳定 `fieldId`，并按权限配置组配置少量例外权限；未配置例外的字段继承权限组默认权限。不同绑定各自保存例外，不回写可复用的表单流程版本。节点按钮事件按具体按钮独立声明；只有声明了事件的按钮才展示事件配置，未声明事件的节点不展示空事件区域。作业流程表单填写节点仅为已声明且选择填充字段的事件绑定真实字段，不重复声明内置事件。

填报节点的批量默认权限操作必须落到真实主体配置；没有主体时不能只改变临时展示。切换表单模板或表单流程版本时，保存前清理不存在于新表单或不再对应新主体的字段例外。以上是配置层规则，不代表表单流程实例、运行时权限解析或审批任务已经实现。

作业流程表单填报节点保存具体表单流程版本引用，作业流程版本发布后锁定该引用；表单流程后续发布新版不自动改变已发布作业流程或在途业务。普通配置入口只展示当前发布版本，历史发布版本不再作为新配置选项，但既有发布快照继续保留。表单流程侧提供使用情况分析，按流程版本查看引用它的作业模板、作业流程版本、表单填报节点和绑定表单；使用情况是由作业流程图派生的查询投影，保存作业流程图、创建继承草稿、发布或复制已发布版本时重建。作业流程草稿引用旧版时界面必须提醒并允许用户显式升级到当前发布版，升级前校验字段权限例外、按钮事件和签名字段绑定兼容性；不兼容时阻断并说明原因。后端暂时保留历史已发布版本可引用的能力，作为未来管理员级版本维护口子；该能力开放前仍需专用权限、提示和审计治理。

已被任何作业流程版本中的表单填报节点引用的表单流程禁止删除；删除前必须先解除相关作业流程引用。该约束保护已发布作业流程版本的可追溯性，避免删除后形成无法解释的历史引用。

### 当前产品制程配置投影

产品管理首版不另建一份用于展示的“知识图”数据。它直接把上述关系保存为可追溯的业务事实，后续知识探索和问答读取同一份关系投影：

| 知识关系 | 当前业务事实 | 关键引用 |
|----------|--------------|----------|
| 产品拥有制程版本 | `ProductProcess` -> `ProductProcessVersion` | `productVersionId` |
| 制程版本绑定路线和 DHR | `ProductProcessVersion` | `routeVersionId`、`dhrTemplateVersionId` |
| 工序属于路线版本且被配置 | `ProductProcessOperationBinding` | `routeNodeKey`、`productProcessVersionId` |
| 工序引用 DHR 中的表单 | `ProductProcessOperationFormBinding` | `dhrTemplateItemId`、`formTemplateVersionId` |
| 工序引用 SOP | `ProductProcessOperationDocumentBinding` | `documentVersionId` |

制程版本的 `productionMode` 作为后端非空字段、接口负载和审计快照一部分继续保留。当前产品规则不再允许前端选择生产模式：新建或复制产生的新版本固定保存“量产”，编辑既有版本时保留原字段值。当前已确认不存在非量产制程，因此不触发历史数据迁移。

制程版本的 `productionForm` 继续作为后端非空字段、接口负载和审计快照一部分保留。产品和产品簇的共享编辑器及产品兼容工作台只提供“批次”和“SN”，后端兼容 Controller 与共享 OwnerService 也只允许保存这两个值；“批次转SN”不再是受支持的生产方式。数据库列结构未改变，取值约束由共享业务保存路径和兼容保存路径共同执行。

因此“产品 A 的制程 V2.0 为什么在装配工序显示某张表单”可以确定性地查到：产品制程版本选择的 DHR 版本、该 DHR 目录项、目录项指向的表单版本，以及装配节点的绑定记录。产品管理界面只负责维护这些关系；未来的知识探索、问答和生产执行快照都必须从这些事实读取，而不是解析页面文案或另存一套关系。

## 规则模型

规则采用结构化事件、条件、结果，而不是只保存一段自然语言：

```yaml
id: operation.complete.required-form
name: 工序完工前检查必填表单
status: implemented
trigger: operation.complete
scope: process-version
condition:
  - operation.formBinding.requiredBeforeComplete == true
  - formInstance.status != completed
result:
  type: block
  reason: required-form-not-completed
explanation:
  template: 工序完工前必须完成表单 {form.name}
```

规则的 `status` 决定它进入哪一种读取投影，而不是决定它是否存在。内部知识投影可以读取全部状态，便于研发维护“已实现什么、未来计划什么”；客户知识投影和运行时投影只读取当前产品发布版本中已经 `verified`、具备执行契约的规则。`planned`、`specified` 和 `unverified` 只能在内部知识库中查询，不向客户问答暴露。

建议状态：

| 状态 | 问答可见 | 运行时可执行 | 说明 |
|------|----------|--------------|------|
| planned | 仅内部 | 否 | 已识别、尚未设计完成 |
| specified | 仅内部 | 否 | 已完成业务定义，尚未实现 |
| implemented | 内部及待发布环境 | 需验证、发布后 | 已有代码和数据结构 |
| verified | 是 | 是 | 已通过场景测试并纳入可执行发布版本 |
| deprecated | 按权限 | 否 | 客户只在确有历史关联时看到必要说明 |

## 当前已确认能力与规划能力

| 能力 | 知识模型记录 | 当前是否进入执行 |
|------|--------------|------------------|
| 租户级车间四字段 CRUD | implemented | 是，按租户查询并审计变更 |
| 车间被产线引用后锁定编码且禁止删除 | implemented | 是 |
| 停用车间不可用于后续新引用 | specified | 否，尚无新业务引用车间的正式接口 |
| 产品来源于产品/半成品物料 | implemented | 是 |
| 产品下多个制程版本并行 | implemented | 是 |
| 制程绑定工艺路线版本 | implemented | 是 |
| 工序引用 DHR 目录中的多个表单 | implemented（配置关系） | 产品管理可维护；运行期校验后续接入 |
| 工序引用多个 SOP | implemented（配置关系） | 产品管理可维护；运行期消费后续接入 |
| 表单结束前完成 | planned | 暂不执行，后续补充 |
| 表单共享 | planned | 暂不执行，后续补充 |
| 表单按钮和字段权限配置 | planned | 暂不执行，后续补充 |
| 工序事件触发作业 | planned | 暂不执行，后续补充 |
| 工序开始前作业校验 | planned | 暂不执行，后续补充 |
| 以当站工序作为最终产出 | planned | 暂不执行，后续补充 |
| 物料齐套校验 | planned | 仅记录，不做 UI 和运行逻辑 |

规划项必须有业务说明、前置依赖和验收场景，但不能出现在当前版本的客户页面、客户问答或可执行配置面板中。这样既不会丢失未来设计，也不会把尚未实现的能力误传给用户。功能完成后，开发者将它从内部知识投影推进到客户知识投影和可执行投影，并补充对应的执行适配器和测试。

## 运行架构

```text
产品制程选择
  -> 查询已发布知识模型和业务事实
  -> 校验产品、路线、DHR、表单和 SOP 关系
  -> 生成产品制程执行快照
  -> 生产服务按快照执行
  -> 规则引擎返回允许/阻断及解释
  -> 审计记录事件、规则版本和快照版本
```

一期不需要引入独立图数据库。建议使用现有关系型数据库保存业务事实和关系表，使用 JSONB 保存规则条件和解释模板，再生成一层面向问答的关系投影。只有当跨域关系查询明显超过关系表的可维护范围时，再评估图数据库。

## 产品布局

### 业务知识探索页

默认是只读的三栏工作台：

```text
左侧：业务域和概念树
中间：关系图 / 业务流程 / 规则链路
右侧：选中对象的属性、关系、规则、证据、影响范围
底部：可展开的来源和审计证据
```

顶部显示当前知识模型发布版本、环境和查询范围。节点显示名称、类型和状态标签。点击“工序”时，中间可以切换为业务流程视图，显示 DHR、表单、SOP 和待实现规则的关系。

### 业务问答页

这是客户可见页面，只使用客户知识投影。页面分为问题历史、回答区和证据区。每个回答必须附带：

- 使用的知识模型版本；
- 命中的规则 ID；
- 关系路径；
- 业务事实和源码/文档来源；
- 当前适用的产品和知识模型版本。

问答层可以使用大模型做意图识别和自然语言组织，但所有事实先通过结构化查询获得；没有证据时必须明确回答“当前产品知识库中未定义”，不能自行补全业务规则，也不能泄露内部规划信息。

### 内部知识维护页

这是研发、产品和实施人员使用的页面，可以查看规划项、依赖、实现状态、代码证据和待办，但不等同于客户问答页面。规划项可以高频调整，维护它不会改变客户当前看到的业务逻辑，也不会改变生产执行。

## 实施顺序

1. 固化核心概念、关系和能力状态，不开发用户编辑器。
2. 将当前产品管理、工艺路线、DHR 模板、表单模板和 SOP 的关系接入模型。
3. 用产品制程版本的“选择路线 -> 绑定 DHR 表单/SOP -> 生成执行快照”做第一个端到端试点。
4. 为已实现流程增加规则解释和证据查询。
5. 再逐项补充表单完工校验、表单共享、作业、最终产出和物料齐套校验。

这样未开发功能不会丢失，也不会提前进入生产逻辑；产品升级时只需要同时更新知识模型、执行契约和对应实现，并保留旧版本解释历史。
